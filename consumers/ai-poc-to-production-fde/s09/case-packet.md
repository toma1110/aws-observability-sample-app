# S09 架空ケース：障害記録の調査を支援する

このケースは演習用の架空設定です。実在の顧客、チーム、障害、業務実績を表しません。ここに記載する組織条件は議論のための仮置きであり、受講者は事実として計測された値と混ぜないでください。

## 顧客からの相談

ある架空の会社では、AWS上の社内注文サービスを運用しています。運用担当者はアラートを受けると、対象リクエストのログを探し、起きたことと追加調査の要否を短くまとめて担当者へ引き継ぎます。顧客は、ログを根拠にした調査の下書きをAIで支援できるか知りたいと考えています。

現在の相談内容から分かるのは、担当者がログを調べて引き継ぐ業務があることだけです。発生頻度、所要時間、影響額、削減目標、利用者数、データ分類、許容費用、SLOは提示されていません。数字が必要な場合は「仮定」と明記し、顧客に確認する項目へ残してください。

## 現在の業務（聞き取り前の仮説）

次の流れは調査対象を考えるための仮説です。実際の担当者へ確認するまでは、顧客の確定した手順として扱いません。

1. アラートまたは問い合わせを受け取る。
2. リクエスト識別子や時間帯を手掛かりに、関連ログを探す。
3. 記録にある事実と、まだ確かめていない原因候補を分ける。
4. 必要なら別のログ、メトリクス、担当者の情報を確認する。
5. 調査結果と次の確認事項を担当者へ引き継ぐ。

## 検討する案

- **現状維持・手順改善:** 検索条件や引継ぎ書式を整え、既存のログ検索で対応する。
- **ルール・検索による補助:** 既知のエラー分類、ダッシュボード、検索リンク、定型テンプレートを使う。
- **AIによる下書き:** 限定されたログを読み取り専用で取得し、根拠付きの調査要約案を作る。人が内容を確認して判断する。

AIが障害を自動修復したり、原因を確定したりすることはこのケースの前提ではありません。書き込み操作や自動対処も対象に含めません。

## 技術検証の引継ぎ

業務条件は架空ケースで考えます。技術上の観測は、別に示すS05/S06の固定版サンプルアプリ実行記録だけを使います。共有アプリは `v1.0.2` / commit `3a3599121537bb83a9b7afd42162a8635aeee59b` です。READMEに従う固定版の手順は[共有アプリREADME](https://github.com/toma1110/aws-observability-sample-app/blob/v1.0.2/README.md)を参照してください。

S05で保存した限定例では、正常・入力拒否・意図した失敗注入・意図した遅延を各1回実行しています。選定した一つのログには `status=500`、`durationMs=0.07`、`error=RuntimeError` が記録されています。この値だけでは原因、影響範囲、顧客影響は分かりません。HTTP 500は教材用アプリの意図した故障注入で、AWSサービス障害の観測ではありません。

同じ選定ログに対するBedrock調査は2応答からなる1回の調査chainです。AIはログの記載値と、ログだけでは分からない事項を分けて返しました。人による同条件の調査時間、AI回答の確認・修正時間、顧客業務での効果、実請求額は確認されていません。180秒（人だけの作業例）と45秒（AI回答を人が確認する作業例）を使う場合は、どちらも演習上の仮定と表示してください。

## 顧客と次に確認すること

- 対象となる作業、利用者、開始から終了までの境界
- 現在の手順、例外、既存ツール、実測可能な業務指標
- 使ってよいデータ、利用目的、契約・法務条件、所在、保持・削除
- end-user認証、tenant境界、アプリとtoolの認可、監査記録
- 誤回答時の確認者、手作業へ戻す方法、運用ownerと障害対応
- 月間/peak負荷、応答目標、Region/model、費用許容範囲
- 継続・縮小・中止を判断する責任者と時点
